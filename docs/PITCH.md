# Pitch kit — Richie Transport Services Management System (RTS)

Ten minutes, one screen at a time, and every number you point at is read back from the running
system. Nothing on the screen is a mock-up.

## Before you start (two minutes, once)

```bash
cd RTS
npm run demo:reset      # stops the app, wipes the local demo data, starts it fresh
```

The server comes up on <http://localhost:3000> and listens on every network interface, so a
projector, a laptop or a phone on the same Wi-Fi can open it. To check it:

```bash
npm run demo:check     # 54 checks: signs in through the real login form and walks every screen
```

`demo:reset` never touches a real database — it refuses to run when `DATABASE_URL` is set.

## The run of show

1. **The landing page** (`/`) — what the system is, in one screen, no jargon.
2. **Sign in as the dispatcher.** The Dispatch Command Centre is the best frame in the product:
   the trip board on the left, the live map in the middle, the inspector on the right.
   - Point at the trip board: *14 duties, 3 on the road, 64 passengers.*
   - Click a duty. The inspector shows the passenger list, the assigned vehicle and driver.
   - Point at the **alerts rail**: *Heavy traffic on Spintex road, pickup running 25 minutes late.*
   - The **event tape** is the history: who departed, when, in what order.
3. **The map is live.** The vehicles are where the phones say they are — the driver's phone posts
   its position, the office sees it. The map refreshes every 15 seconds.
4. **The driver, on a phone.** Sign in as `driver.abena@` and open `/driver` — the trip list, the
   passenger manifest, and **Start sharing** on the trip screen. The phone shares its position
   while the trip runs, queues it offline and syncs when the network returns. Switch back to the
   dispatcher and the vehicle has moved.
5. **Money.** Sign in as the finance officer, open `/finance`:
   - *Invoiced, collected, outstanding, overdue* — the four numbers an owner asks for first.
   - Invoice lines, then the **PDF** link: a real invoice document, generated by the server.
   - **Payment link** on an invoice: with a payment provider configured this produces a real
     Paystack/Flutterwave page; without one it says invoices are settled by transfer. Either way it
   is honest.
6. **The fleet and the safety record.** `/fleet` — vehicles, fuel, inspections, maintenance due.
   `/incidents` — the breakdown and safety workflow an operator actually follows.
7. **The audit trail.** `/audit` — every sensitive action is written down, with the person and the
   time. This is the slide that wins over a sceptical manager.
8. **Close with the proof.** On your laptop, not the slides:

```bash
npm run demo:check        # 54 checks, every figure read back from the running server
npm run test:sso          # the single sign-on flow, end to end
npm run test:delivery     # a real message through a stand-in SMS gateway
```

## If someone asks "is it real?"

| Question | The true answer |
| --- | --- |
| Does the phone really track the driver? | Yes. The phone posts its GPS to the server; the office sees the fix and its age. It queues offline and syncs. |
| Are the messages real? | The SMS (Hubtel) and e-mail (SMTP) clients are real and tested. With keys configured a message leaves the building and the delivery is recorded with the provider's message id. Without keys the message stays in the app and the screen says so. |
| Is the map a picture? | With a Mapbox token it is a real basemap and the markers sit where the vehicles are. Without one it draws the built-in corridor, and the caption says which. |
| Is the route plan optimal? | It is a real solver (Clarke-Wright savings with a 2-opt pass), not OR-Tools. The screen says so and names the upgrade path. |
| Where does the data live? | PostgreSQL in production (or PGlite locally, which is the same engine in-process). 42 tables, 7 migrations, applied at boot. |
| Can we run it on our own server? | Yes — one container or `npm ci && npm run build && npm start`. See `docs/OPERATIONS.md` §5. |
| Who can see what? | Six roles, one permission matrix, enforced on the server for every action. `npm run roles` prints what each role can reach. |
| Can we trust the numbers? | Every figure on screen is read from the database. The demo script re-reads them after each action. |

## The two-minute version for a busy owner

> One system for the three problems: staff are picked up and dropped off on time, vehicles and
> drivers are accounted for, and the invoices come in. The dispatcher sees every duty on one
> screen, the driver sees only their own trip on their phone, and the finance officer sees what
> is owed and what has been paid. Every action is logged.

Then show the Dispatch Command Centre, the driver phone, and the four finance numbers.
